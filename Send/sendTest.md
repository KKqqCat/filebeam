# filebeam V1 需求与技术设计

## 1. 项目定位

`filebeam` 是一个局域网点对点文件传输工具。在同一网络下，一台机器作为接收端监听，另一台作为发送端连接并把一个文件发过去，接收端保存到磁盘。

真实使用场景：两台机器之间传一个文件，不想用 U 盘、云盘或聊天软件中转。

本程序是学习路线的第一个网络程序，重点训练：

- TCP socket 编程：`socket`、`bind`、`listen`、`accept`、`connect`。
- 核心认知：**TCP 是字节流，不是消息**。一次 `recv` 可能只收到半条消息，也可能一次收到多条消息的一部分。
- 应用层协议设计：定长头部 + 变长负载，自己划定消息边界。
- 部分读写：`send`/`recv` 都可能只处理了部分字节，必须循环。
- 大文件分块传输，不一次性读入内存。
- 文件描述符和 socket 的 RAII 管理。
- 连接正常关闭、异常断开和资源释放。
- 传输完整性校验：收到的文件必须和原文件逐字节一致。

V1 使用 C++17，只做**阻塞式、单连接、一次传一个文件**。不涉及并发、`poll`/`epoll`、加密、断点续传、多文件——这些留给后续程序，避免第一个网络程序被淹没。

预计生产代码 500～800 行，开发周期 5～6 天。只用 POSIX socket API，不引入第三方网络库。

## 2. 命令行接口

一个可执行文件 `filebeam`，通过子命令区分收发两端：

```text
filebeam recv --port PORT --out DIR [--overwrite]
filebeam send --host HOST --port PORT --file PATH
filebeam help
```

### 2.1 接收端 recv

- `--port PORT`：监听端口，`1..65535`。
- `--out DIR`：保存目录，必须已存在且是目录。
- `--overwrite`：可选。目标文件已存在时是否覆盖，默认不覆盖。
- 行为：绑定端口、监听、接受一个连接、接收一个文件、保存、退出。
- V1 只处理一个连接就退出，不需要循环服务多个客户端。

### 2.2 发送端 send

- `--host HOST`：接收端地址，支持点分十进制 IPv4，如 `192.168.1.10`；是否支持主机名由实现决定。
- `--port PORT`：接收端端口。
- `--file PATH`：要发送的文件，必须存在且是普通文件。
- 行为：连接、发送文件、等待接收端确认、退出。

### 2.3 通用规则

- 未知子命令、未知选项、缺少必要参数、参数值非法属于命令行错误。
- `help` 输出用法后成功退出。
- 端口非数字、越界，都是命令行错误。

## 3. 应用层协议（重点）

这是本程序的核心。TCP 只保证字节按序到达，不保证一次 `recv` 的边界，所以必须自己设计协议来划定“文件名多长、文件内容多长、从哪里结束”。

### 3.1 协议总览

一次传输的字节流按顺序分为三段：

```text
[ 固定头部 ] [ 文件名字节 ] [ 文件内容字节 ]
```

传输结束后，接收端回送一个结果响应。

### 3.2 固定头部

建议头部为固定长度，包含：

- magic：一个固定标识，例如 4 字节，用于识别协议和快速拒绝乱连。
- version：1 字节协议版本，V1 为 `1`。
- name_len：文件名长度，建议 2 字节无符号，限制文件名不超过一个合理上限（如 255 或 4096 字节）。
- file_size：文件内容长度，8 字节无符号，支持大文件。

### 3.3 字节序

- 头部中所有多字节整数使用**网络字节序（大端）**。
- 发送前用 `htons`/`htonl` 或等价方式转换，接收后转回主机序。
- 这是跨机器通信必须处理的问题：不同 CPU 的字节序可能不同，不能直接把结构体内存原样发出去。

### 3.4 文件名

- 紧跟头部，长度为 `name_len`。
- 只传文件名本身，不传路径。发送端应对 `--file` 取 basename。
- 接收端保存时，文件名中的路径分隔符、`..`、绝对路径都必须被拒绝或安全化处理，防止把文件写到 `--out` 目录之外（目录穿越攻击）。这是安全要点，必须处理。

### 3.5 文件内容

- 紧跟文件名，长度为 `file_size`。
- 分块发送和接收，每块固定缓冲区（如 64 KiB），不要求把整个文件读入内存。

### 3.6 结果响应

接收端在收完并落盘后，向发送端回送一个简单响应，至少能区分：

- 成功。
- 失败（如磁盘写入错误、文件名非法、目标已存在且未 `--overwrite`）。

响应格式可以简单，例如 1 字节状态码。发送端读到响应后据此决定退出码。V1 不要求把详细错误文本回传。

## 4. 字节流处理（第二个重点）

必须正确处理 TCP 的字节流特性，这是网络程序最常见的 bug 来源。

### 4.1 完整发送

- `send` 的返回值可能小于请求发送的字节数。
- 必须循环发送，直到全部字节发出，或出错。
- 封装一个“发送 N 字节”的函数，内部循环处理部分写。

### 4.2 完整接收

- `recv` 一次可能返回比请求少的字节，也可能把属于下一段的数据一起带来。
- 接收固定长度数据（头部、文件名、每一块内容）时，必须循环 `recv` 直到凑够需要的字节数。
- 封装一个“精确接收 N 字节”的函数，内部循环。
- `recv` 返回 `0` 表示对端关闭连接。如果此时还没收满预期字节，是提前断开错误，不能当作正常结束。

### 4.3 边界与异常

必须明确处理：

- 头部 magic 或 version 不匹配：拒绝并报错。
- `name_len` 或 `file_size` 超过约定上限：拒绝，防止恶意超大声明导致资源耗尽。
- 声明的 `file_size` 与实际收到的字节数不一致（对端中途断开）：视为失败，不能保留半个文件当成功。
- 发送端读文件时文件变短或出错：需要有合理处理。

## 5. 文件落盘与完整性

### 5.1 落盘

- 接收端把内容写入 `--out` 目录下、以安全化后的文件名命名的文件。
- 建议先写临时文件，全部接收并校验成功后再 `rename` 为最终文件名。这样中途失败不会留下一个看起来正常、实则不完整的文件。（复用你在 todo 程序里学到的原子写入思想。）
- 目标文件已存在且未指定 `--overwrite` 时，拒绝并回送失败响应。

### 5.2 完整性

- V1 至少通过“实际接收字节数等于声明的 `file_size`”来判断完整。
- 更强的完整性校验（如校验和/哈希）不是 V1 硬性要求，但如果你想加，可以在头部或响应中加入一个内容哈希，接收端比对。是否实现由你决定；若不实现，需在 README 说明当前完整性保证的边界。

### 5.3 验收标准

传一个文件后，接收端保存的文件必须和发送端原文件**逐字节完全一致**，可用哈希比对验证。空文件、小文件、大于缓冲区的文件、二进制文件都要正确。

## 6. 资源管理

- socket 文件描述符必须用 RAII 封装：构造/获取时持有 fd，析构时 `close`，禁止拷贝，允许移动。
- 不允许裸的 `close` 散落在多个返回路径上导致遗漏或重复关闭。
- 监听 socket 和连接 socket 都要正确关闭。
- 文件流用 RAII（`std::ifstream`/`std::ofstream`）。
- 出错提前返回时，已经打开的资源必须被释放。
- 不使用全局可变状态，不使用裸 `new`/`delete`。

### 6.1 SIGPIPE

- 向已被对端关闭的连接写数据，默认会触发 `SIGPIPE` 信号使进程直接终止。
- 必须处理：可以忽略 `SIGPIPE`（如 `signal(SIGPIPE, SIG_IGN)`），或在 `send` 时使用 `MSG_NOSIGNAL` 标志，然后按 `send` 返回的错误处理。
- 这是网络编程一个经典陷阱，V1 必须显式处理，并在 README 说明选了哪种方式。

## 7. 退出状态

| 退出码 | 含义 |
|---:|---|
| `0` | 传输成功，或正常显示帮助 |
| `2` | 命令行使用错误 |
| `3` | 运行错误：连接失败、协议错误、传输中断、文件读写失败、被接收端拒绝 |
| 其他非零 | 未预期错误 |

- 诊断信息写 `stderr`，简短的成功信息可写 `stdout` 或 `stderr`，由实现决定但要一致。
- 发送端根据接收端的失败响应，也应返回非零退出码。

## 8. 建议模块划分

模块名和函数签名由开发者决定，建议保持以下职责边界。

### 8.1 Socket RAII 封装

- 一个持有 fd 的类，析构自动 `close`，禁拷贝、可移动。
- 可提供便捷方法或自由函数完成 `bind`/`listen`/`accept`/`connect`。

### 8.2 字节流收发工具

- `send_all(fd, buf, len)`：循环发送直到完成或出错。
- `recv_exact(fd, buf, len)`：循环接收直到收满或出错/对端关闭。
- 这两个函数是整个程序正确性的地基，建议单独、可测试。

### 8.3 协议编解码

- 头部的序列化和反序列化，处理字节序。
- 与网络 I/O 解耦：编解码只处理内存中的字节缓冲，不直接调用 `recv`/`send`，这样可以脱离网络单元测试。

### 8.4 发送端逻辑

- 连接、组装并发送头部、文件名、分块发送内容、读取响应。

### 8.5 接收端逻辑

- 监听、接受连接、接收并校验头部、接收文件名并安全化、分块接收内容落盘、回送响应。

### 8.6 Cli 与 main

- 解析子命令和参数。
- 分发到发送端或接收端逻辑。
- 映射退出码。

建议：协议编解码和字节流工具尽量与具体 socket 解耦，便于测试；网络部分可以用本机 `127.0.0.1` 回环做集成测试。

## 9. 建议工程结构

```text
filebeam/
├── CMakeLists.txt
├── README.md
├── designDocument/
│   └── filebeam-V1-需求与技术设计.md
└── src/
    ├── main.cpp
    ├── Socket.hpp/.cpp        # RAII socket
    ├── NetIO.hpp/.cpp         # send_all / recv_exact
    ├── Protocol.hpp/.cpp      # 头部编解码、字节序
    ├── Sender.hpp/.cpp
    ├── Receiver.hpp/.cpp
    └── Cli.hpp/.cpp
```

名称可调整，但网络 I/O、协议编解码和 CLI 应分离，业务逻辑不要堆在 `main.cpp`。

CMake 要求：

- C++17，关闭编译器扩展。
- `-Wall -Wextra -Wpedantic -Wshadow -Wconversion`，尽量清零。
- 可选 ASan/UBSan 开关。
- 测试目标本轮不强制；若加，用 CTest 注册。

## 10. 验收场景

以下用两个终端在同一台机器上用回环地址 `127.0.0.1` 即可验证，不需要两台真机。

1. 基本传输：
   - 终端 A：`filebeam recv --port 9000 --out /tmp/recv`
   - 终端 B：`filebeam send --host 127.0.0.1 --port 9000 --file test.txt`
   - 结果：`/tmp/recv/test.txt` 出现，内容与 `test.txt` 逐字节一致，两端都返回 `0`。

2. 空文件：`file_size` 为 0 的文件能正确传输，接收端得到一个 0 字节文件。

3. 大文件：明显大于缓冲区（如几十 MB）的文件，分块传输后逐字节一致，进程内存不随文件大小线性膨胀。

4. 二进制文件：含 `\0` 和任意字节的文件正确传输，不被当作文本截断。

5. 文件名带空格或中文：正确保存，不损坏。

6. 覆盖策略：
   - 目标已存在且未加 `--overwrite`：接收端拒绝，回送失败，发送端非零退出，原文件不被破坏。
   - 加 `--overwrite`：正常覆盖。

7. 目录穿越防护：发送端构造文件名为 `../evil` 或绝对路径时，接收端不能把文件写到 `--out` 之外。

8. 连接失败：接收端未启动时，发送端 `connect` 失败，返回 `3` 并有清晰诊断。

9. 提前断开：发送端在发送中途被终止，接收端检测到连接关闭且字节不足，判定失败，不保留半个文件。

10. SIGPIPE：接收端在传输中途关闭，发送端不因 `SIGPIPE` 直接崩溃，而是走正常错误处理返回 `3`。

11. 命令行错误：缺少 `--port`、非法端口、未知子命令返回 `2`。

## 11. 建议测试方向

网络程序的测试分两层。

### 不依赖网络的单元测试

- 协议头部编解码往返：给定文件名和大小，编码再解码得到相同值。
- 字节序：构造已知字节序列，验证解析结果，确保大端处理正确。
- 文件名安全化：`../a`、`/etc/passwd`、`a/b`、正常名，验证是否被正确拒绝或转为安全名。
- `send_all`/`recv_exact` 可用一对 `socketpair` 或管道做本地测试，模拟部分读写。

### 集成测试

- 用 `127.0.0.1` 起接收端，再跑发送端，比对文件哈希。
- 空文件、大文件、二进制文件。
- 目标已存在的覆盖行为。
- 目录穿越文件名被拒绝。

可以用固定内容生成测试文件，用 `cmp` 或哈希比对收发结果。

## 12. 完成定义

V1 完成需满足：

- 能在回环地址上把一个文件从发送端传到接收端，逐字节一致。
- 正确处理空文件、大文件、二进制文件、带特殊字符的文件名。
- 头部使用网络字节序，能跨字节序机器工作（至少设计上正确）。
- `send_all`/`recv_exact` 正确处理部分读写和对端关闭。
- 协议边界、非法头部、超大声明、中途断开都被正确识别为失败，不产生损坏文件。
- 目录穿越文件名被防护。
- socket 用 RAII 管理，无 fd 泄漏。
- 显式处理 SIGPIPE。
- 覆盖策略正确。
- 退出码符合契约。
- 编译警告基本清零，ASan/UBSan 无报告。
- README 说明构建、运行、协议格式、退出码、SIGPIPE 处理方式和已知限制。

## 13. 开发顺序建议

1. 先写 Socket RAII 封装和 `send_all`/`recv_exact`，用 `socketpair` 或回环验证部分读写。
2. 写协议头部编解码，处理字节序，单元测试往返。
3. 实现接收端：监听、接受、收头部、收文件名、分块收内容、落盘（先不做安全化和临时文件）。
4. 实现发送端：连接、发头部、发文件名、分块发内容、收响应。
5. 打通回环基本传输，用小文本文件跑通并比对。
6. 加空文件、大文件、二进制文件测试。
7. 加文件名安全化、临时文件原子落盘、覆盖策略。
8. 加 SIGPIPE 处理、各类错误路径和退出码。
9. 写 README，跑警告和 Sanitizer。

允许在实现中调整模块接口和协议细节。如果改变协议格式、安全策略或退出码语义，需在 README 或 Review 中说明原因。

V1 通过后，我会以用户身份追加一次合理的需求变更。

## 14. 需要你先想清楚的问题

开始写之前，建议先在脑子里回答这几个网络编程的关键问题，这比代码本身更重要：

1. 接收端怎么知道文件名有多长、文件内容有多长、内容到哪里结束？（答案在协议头部）
2. 如果一次 `recv` 只返回了半个头部，你的代码会怎样？
3. 如果一次 `recv` 把头部和一部分文件内容一起返回了，你会不会把多读的字节丢掉？
4. `send` 返回值小于你要发的长度时，剩下的字节怎么办？
5. 对端在你写数据时突然关闭，你的进程会发生什么？怎么避免被信号杀死？
6. 收到一半连接断了，你怎么保证不会留下一个“看起来正常”的残缺文件？
7. 发送端声称文件名是 `../../etc/passwd`，你的接收端会把文件写到哪里？

这些问题想清楚了，代码只是把答案写出来。想不清楚，代码一定会在真实网络里出问题。
